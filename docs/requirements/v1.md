# JobArk V1 需求与验收标准

## 1. 产品目标

JobArk 是个人使用的 AI 求职工作台。V1 的目标是让用户完成从真实职业资料维护、职位录入与匹配，到投递过程跟踪和数据查看的闭环。

本文件定义稳定的产品需求和验收标准，不记录任务进度、实现方案或临时拆解。

## 2. V1 范围

### 2.1 个人资料（Profile）

- 用户可以在个人资料页维护基本信息、技能、工作经历、项目、教育和语言；求职偏好在独立的「求职策略」页面维护。
- 每项可用于匹配或简历的主张应能关联真实证据；不确定信息必须明确标记，不能伪装为已验证事实。
- 首次建档可上传带文字层的 PDF 或 HTML 简历；本地提取文本后，只有用户明确同意才发送到已配置的**大模型服务**（用户可见文案统一使用"大模型服务"，不再称"AI 网关"）。导入入口以主按钮「从已有简历导入」呈现，选择后直接弹出文件选择弹窗（不要求用户再点一次同名按钮），弹窗提供文件选择并先说明：将从 PDF/HTML 本地提取的简历文字发送到已配置的大模型服务、可能包含姓名与联系方式、不会自动写入个人档案、仅在用户确认后才落库；弹窗内在「继续」旁以醒目（危险色）小字提示该动作的后果：将把本地提取的简历文字发送到已配置的大模型服务，短暂连接或服务错误时最多自动重试一次。用户点击「继续」即构成明确同意并调用预览接口，不再要求额外勾选——勾选只是多一步操作，并不增加知情程度；未选择文件时不得发起外发请求。预览失败（超时、网络、服务异常）必须在弹窗内就地反馈并保留 `request_id`。
- AI 结果先展示为可逐项取舍的候选，确认后才写入档案；已有档案导入不得覆盖现有事实，只能作为补充候选事实。根协议错误安全失败；单个候选的结构或原文证据失败只排除该条，预览必须明确标为部分结果并列出遗漏。项目经历的名称与原文摘录是不可放宽的锚点；角色、说明、职责、成果、技术栈、链接和日期若缺少摘录证据，必须清空并提示，不得连带丢弃已证实的项目骨架。模型返回的未映射字段不得静默作为事实导入；为兼容模型沿用工作经历字段命名，项目条目对项目名称的等价字段（如 `title`）与字符串形式的技术栈做可见的字段归一化，归一化后仍须通过与其它字段同等严格的原文校验。预览仅可对明确的短暂连接、429、5xx 错误自动重试一次，超时、协议、结构和证据错误不得重试。
- 导入采集覆盖基本信息（含个人简介与公开链接）、技能、工作经历、项目经历与教育经历。候选在确认前可逐字段修正与补全，来源摘录只读；写入后的条目仍可在档案页各事实面板中继续编辑。被用户修正到原文摘录之外的条目，来源记为本人陈述，不得伪装成简历原文，且与未修正条目一样保持"未验证"。
- **来源证据不是使用门槛**：技能、工作经历、项目经历、教育经历与语言的来源证据一律可选。无来源的条目可以正常保存、编辑、展示、参与职位匹配与简历候选生成。只有把技能标为「已验证」时才要求挂上有效证据——该约束在应用层与数据库层同时生效，必须保留，且不得为了"让无来源条目可用"而删除。
- 必须区分「用户认可内容可用」与「系统已独立核实」：用户确认导入后内容即可作为档案事实使用（匹配与简历生成都读得到），但这**不等于**独立核验。导入与手工填写产生的事实一律保持未验证状态，界面与报告都不得把"用户确认"表述为"已核实能力"。系统仍需保留来源记录与状态，以便区分"简历原文"与"本人填写"、以及"有来源记录"与"已证明能力"。
- **导入候选的条目来源语义**：每个候选条目必须显式标注来源（`origin`），取值为 `RESUME`（本条目内容来自简历原文）或 `MANUAL`（本条目为本人填写）。`RESUME` 条目必须携带真实原文摘录，预览阶段逐字校验摘录确实存在于上传文件；其字段取值仍须落在该摘录内。`MANUAL` 条目**禁止携带摘录**（携带即 422），只做必填、长度、日期顺序、重复项等领域校验，并按「本人填写」记录来源。用户把 AI 条目改到摘录之外、或在候选页新建条目时，该条自动转为 `MANUAL`；改到摘录之外的内容不得继续沿用旧摘录作为来源证明。不得通过填写假摘录、复制无关摘录或整体关闭原文校验来新增条目。
- 导入候选支持完整的人工修订：修改 AI 识别错误的基本信息与四类事实、新增 AI 完全漏掉的条目、删除或排除错误条目、补充简历未提供的可选字段，并在确认前看清最终将写入的内容。用户新增条目同样要满足必填与领域约束，错误按字段返回（422 + 字段路径）；确认前页面必须能指出缺少哪些必填项。文件哈希核对、预览不写库、确认才写库、已有档案导入去重规则（只补充未重复条目）保持不变。
- 确认操作的文案表达为「我已核对，这些内容可以加入个人档案并用于匹配和简历候选」，不得写成「我证明了所有内容均已验证」。该确认以两步呈现：点「确认」按钮打开二次确认弹窗，弹窗内再确认一次才写入；不再使用常驻勾选框，因为候选在按下确认前会被反复修改，"已经勾过"随时可能已经过期，而弹窗每次点击都重新询问，用户核对的是这一次要写入的内容。取消弹窗不得写入，且下次点击必须重新询问。确认后日常档案列表与编辑流程聚焦内容本身，不再要求用户选择来源或核对原文；来源与状态由系统按导入/本人填写的流程自动记录，仍可在用户排查错误或理解匹配依据时查看。后续编辑已确认档案时不得要求重新上传简历或补交证明；被修改的内容按「本人填写」重新归因，历史来源记录不删除。
- 匹配报告中的命中状态必须区分「档案事实字面匹配」与「该事实另挂来源证据」：报告要说明命中来自档案事实的字面匹配并显示其验证状态（例如未验证），不得暗示技能熟练度、使用年限或整项岗位条件已核实，也不得输出招聘概率。
- 档案尚未创建时，页面提供"手动创建个人档案"与"从已有简历导入"两条互斥路径：两条路径都在**当前页动态展开**，不跳转到独立页面；选择导入时隐藏手动创建表单，避免两个表单同时堆叠。同一入口只出现一次：页面已经提供「从已有简历导入」按钮时，展开区不得再重复该按钮（否则用户会以为点错了入口），未生成候选时给出下一步提示而不是空白区。候选核对页提供"确认使用候选并创建个人档案"与"返回手动创建"。确认后仅把用户勾选且已核对的候选经既有确认接口落库，成功后刷新档案聚合并展示正式档案。返回手动创建不写库、也不清空已选文件与内存候选，便于再次进入核对。已有档案时导入只能补充事实，不能覆盖既有基本信息。
- 字段缺失规则：表单存在但简历未提供的可选字段，在候选中显示为空输入框，不伪造默认值、也不因留空而隐藏字段；确认时写为 `null` 或空数组而不是空字符串，不产生无意义的空事实。必填领域约束（姓名、技能名、公司、职位、工作开始日期等）不因简历缺失而放宽：用户必须补充、取消该条或不予选择该条。候选编辑后来源摘录保持只读；用户补充到摘录之外的事实沿用"本人陈述 / 未验证"证据边界，不得冒充来自简历。
- 候选条目的界面密度随字段数量而定：技能候选固定一行两列，技能名作为卡片主体单独占一行、字号与字重高于次要信息并保证完整显示，原文出处下沉到卡片底部且字号更小，整卡只保留技能名、原文出处与图标删除按钮（不显示字段标签、不提供勾选框；图标按钮必须有可访问名称，窄屏自动变为一列）。点击技能名进入编辑态，回车或失焦即完成编辑；删除会把该条从候选中移除并重建提交下标，避免下标错位后提交到别的技能。工作经历、项目经历与教育经历字段较多，仍按卡片展示并保留勾选框与只读摘录。
- 提供一个不在前端暴露的档案重置接口，仅供本地维护清理：物理删除档案全部数据（含资料修订），回到未创建状态；简历版本或匹配结果仍引用档案数据时拒绝执行并返回可理解的错误。

**验收：**用户能新增、编辑、删除并查看上述资料；教育与工作经历在建档后可见；导入支持格式、大小和空文本校验，扫描版 PDF 无文字层时给出明确反馈；候选可核对来源摘录并逐项取舍，未确认、模型失败或大模型服务未配置时不得写入事实；无效输入、找不到资源和冲突更新返回统一错误格式。

「求职策略」作为侧栏独立入口，承载现有目标地点、职位类型、薪资范围、远程偏好和排除条件表单；个人资料页不展示求职偏好的摘要、操作或跳转入口。未创建个人档案时，策略页引导先建档；加载与保存失败要保留错误反馈和重试。此次仅调整页面归属，继续使用现有偏好数据和 API；渠道配置、多维黑白名单及关键词筛选不在本次范围。当前偏好尚未被职位匹配自动执行，界面不得声称已生效为筛选规则。

导入预览失败时，后端日志应能通过 `request_id` 定位本地解析、默认模型解析、上游请求、候选结构和原文摘录校验中的失败阶段；日志不得包含文件原文、候选内容、上游响应正文或凭据。唯一例外是默认关闭的本地诊断开关 `JOBARK_AI_LOG_MODEL_OUTPUT`：显式开启后才会把模型返回的 JSON 原文以带明确警示标记的日志行输出，仅用于在 local/test 排查候选为何缺失、被清空或被改写；生产环境由配置校验直接拒绝开启。

生成导入预览期间，页面持续显示忙碌状态与两段真实进度：上传阶段显示浏览器上报的请求体字节进度（浏览器不提供总字节数时不显示百分比），模型阶段显示后端已完成的处理阶段。两者都来自同一次请求的真实数据，不虚构百分比。流中成功结果仍是待人工核对的候选，失败含安全错误码与 `request_id`，断流应明确提示失败；原有 JSON 预览接口保持可用。

"项目经历"必须按其业务语义进入候选并可确认写入：简历中的项目包含名称、角色、技术栈、项目说明与日期时应生成完整候选项目；仅有项目名称与有效摘录时保留项目骨架并把缺少证据的可选字段显示为空，而不是丢弃整条项目；模型沿用工作经历字段命名（如用 `title` 表示项目名称）或把技术栈写成字符串时，应在归一化后仍生成候选，并在 `warnings` 中可见。回归测试需覆盖上述路径以及确认写入后的项目事实。

基本信息表单（手动创建与档案页编辑两处）采用**离开输入框即自动保存**：不再提供保存按钮；没有改动不发请求；创建模式在填好姓名并离开输入框后自动创建档案；姓名留空或公开链接只填一半时先不保存并在对应字段给出提示（草稿保留在输入框里）；保存状态必须持续可见（正在保存／有改动未保存／已保存），失败时保留用户输入并就地给出原因，绝不静默丢弃。连续编辑必须使用最新版本号（保存响应即返回新版本），不得因页面尚未重新加载而误报冲突。回归测试需覆盖上述各条，包括"无改动不发请求"。

档案尚未创建时，"手动创建个人档案"与"从已有简历导入"互斥展示；确认导入后生成正式档案并刷新聚合；返回手动创建不落库且保留内存候选。候选页与创建档案页必须由同一个布局组件（`frontend/src/features/profile/components/ProfileBasicsSection.vue`）渲染基本信息，复用同一套字段定义、顺序、标签、帮助文本、控件形态与网格：桌面端每行最多两个普通字段，长文本字段（个人简介、职责、成果、原文摘录）独占一行，窄屏自动变为单列且页面不横向溢出。两条路径的字段集合必须完全一致：候选契约（`ImportCandidate`）与创建档案表单一一样包含姓名、一句话头衔、个人简介、邮箱、手机、所在城市与公开链接，字段集合不得由任一页面硬编码；回归测试需逐字段比较两页的标签、控件形态、占位符、长度上限与必填标记，并断言两页都有同一个公开链接编辑区。所在城市使用共享的省份／城市两级选择器，直辖市可直接选为城市；旧档案及导入候选中的城市字符串应能回显，无法映射到中国城市列表的值仍可保留或手动填写，不得在保存其他字段时被清空。选填字段缺失时显示为空、确认时写为 `null`/空数组；姓名等必填领域约束不因简历缺失而放宽。

个人简介与公开链接（两条路径共有的字段）按字段级隔离校验：模型给出的取值必须能在简历原文中逐字定位（链接地址按去掉协议前缀后比较，名称也要来自原文），定位不到时只清空这两个字段并通过 `warnings` 说明，不得因此丢弃同一份简历的其它候选；确认阶段用户补充到摘录之外的内容属于本人陈述。确认导入只在新建档案时写入这两个字段，已有档案不覆盖既有值，界面必须把这两个字段显示为只读并说明原因，不允许“填了却被静默丢弃”。回归测试需覆盖：可定位时进入候选并写入、不可定位时清空且其它候选不受影响、已有档案不被覆盖。诊断信息中的分组与字段名（`basics`、`summary`、`links` 等后端键名）在界面上必须以中文呈现。

用户可见的 UI 文案、OpenAPI 描述、本需求文档、架构文档与 `docs/ai-gateway.md` 统一使用"大模型服务"；术语替换不得重命名底层 Python 模块、环境变量或兼容 API，也不得静默破坏既有配置。

无来源的手工技能可以保存并参与匹配与简历候选：回归测试需覆盖"创建技能时不传 `source_evidence_id` 也能保存、能在匹配报告中命中、能被写进简历文档"，以及"把无来源技能标为已验证仍被 422 拒绝"。导入候选的回归测试需覆盖：AI 摘录错误时不得冒充简历内容；用户在候选页修改、新增、删除各类条目；新增条目无需摘录即可写入并立即可用；被修改内容不再归因于旧摘录；确认不会把内容标为已验证；确认后编辑不需要重新导入或补证据。为在未配置模型时联调导入链路，提供默认关闭的内置夹具 `JOBARK_PROFILE_IMPORT_FIXTURE`：用内置样例简历与固定抽取结果替代大模型调用，仍走完整的候选校验与确认写库流程。夹具只替换"外部输入"，不放宽任何证据校验；预览带 `fixture` 标记，界面必须明确提示"内置模拟数据，未调用大模型服务"，且该标记要延续到确认成功提示中。仅 local/test 可用，生产环境启动即拒绝开启。

### 2.2 简历（Resume）

- 用户可以创建多份简历方向并保存多个不可变 ResumeVersion。
- 用户可以结构化编辑、实时预览，并查看任一次申请所使用的版本。
- AI 优化只能生成候选修改，不能编造事实，且必须支持确认前对比。

**验收：**历史申请绑定的 ResumeVersion 在后续编辑后仍可原样查看；候选内容未确认前不会覆盖正式版本。

### 2.3 职位与匹配（Job & Matching）

- 用户可以手动录入职位和 JD，系统保存 Company、JobOpportunity、JobPosting、JobSnapshot。
- 系统分别计算 Profile Match 与 Resume Match，并展示硬性条件、证据、缺口和不确定项。
- JD 解析失败时保留原始 JD 和安全错误信息，不产生伪造的结构化数据。

**验收：**匹配结果可定位到具体 JobSnapshot 与 Profile/ResumeVersion；页面不只显示单一百分比分数。

### 2.4 申请流程（Application）

- 用户可以从职位创建 Application，选择 ResumeVersion，并记录状态变化。
- 所有状态变化以 ApplicationEvent 记录；当前状态是事件投影，不是散落在 Job 上的布尔字段。
- **显式确认交互**只用于资料外发、不可逆/语义重大的写入，以及服务端识别出的重复申请：用户先填写表单并点击主操作，前端再展示包含具体影响、取消入口和明确确认按钮的二次弹窗；仅点击弹窗确认后才携带对应的 `confirm_external`、`confirm_applied` 或 `confirm_repeat=true` 请求。常规本地保存、创建首个申请和候选条目取舍不增加确认弹窗，避免确认疲劳。取消或关闭弹窗不得发请求，也不得清空表单。重复申请不能靠一个预先勾选的复选框绕过：先按 `confirm_repeat=false` 创建，服务端返回稳定的“已有申请”冲突码后，才展示“创建新的申请尝试”弹窗并以 `confirm_repeat=true` 重试；其他冲突仍在原表单上下文提示。AI 简历优化和 AI JD 解析的弹窗必须说明发送范围与潜在个人信息；记录 `APPLIED` 的弹窗必须说明系统只记录用户已完成的外部投递、不会代为投递。

**验收：**可以查看完整时间线；非法状态跳转、重复申请等情况有明确处理规则和错误反馈。

### 2.5 Dashboard

- 工作台首页默认进入 Dashboard；侧栏优先展示"概览"，个人资料仍保留独立入口。
- 用户可以查看待处理职位、求职漏斗、来源分布、趋势和简历版本转化。
- 图表使用 ECharts，但每个核心图表都必须有数值或表格替代。

**验收：**访问 `/` 进入 Dashboard，侧栏首项为"概览"；Dashboard 指标可从 ApplicationEvent 与关联数据复算；无数据时页面有明确空状态。

### 2.6 AI 模型配置

- 用户可以维护多个 OpenAI 兼容服务商和模型配置，并设置唯一默认启用模型；首条模型自动成为默认。
- API Key 以可逆加密形式保存，读取时只显示掩码；默认模型只用于既有的受控 AI 候选功能，不能绕过用户对资料外发的明确同意。

**验收：**多个服务商/模型可保存并切换唯一默认模型；连接测试失败不写业务事实；API Key 不在 API、页面或日志中以明文或密文暴露；非安全地址、无可用默认模型和非法状态变更给出统一错误契约。详细范围与验收见 [AI 模型配置](ai-model-configuration.md)。

## 3. V1 不做

- 自动提交申请、自动打招呼或无人确认的浏览器操作。
- 多 Agent、LangGraph、微服务、消息队列、RAG/向量数据库、多租户和移动端。
- 未经验证的平台抓取、登录绕过、验证码绕过或违反平台条款的自动化。
- 厂商专有 SDK、用途级模型分配、模型调用计费统计和自动模型路由。

## 4. 非功能要求

- 后端使用 FastAPI；前端使用 Vue 3、TypeScript、Vite、Ant Design Vue 和 ECharts；数据库使用 PostgreSQL。
- 所有 API 返回遵从 `AGENTS.md` 规定的统一响应与错误契约。
- 所有业务数据变更经 Alembic 迁移管理；敏感配置通过环境变量管理，不提交凭据或真实个人数据。
- 新功能必须覆盖正常路径与关键失败路径，并通过对应的类型检查、lint、测试或构建验证。

### 4.1 前端错误反馈分流

前端只对"无法定位到字段、且不会让页面失去理解"的失败使用全局通知（右上角、约 5 秒自动关闭、同屏最多 3 条、短时间相同错误去重）；其余失败必须留在用户当时的操作上下文里：

- `422 VALIDATION_ERROR`：在字段下方与表单摘要中展示，不得只弹通知。
- 页面初始加载失败：保留页面内提示与"重新加载"入口，不用会自动消失的通知替代。
- 弹窗内提交失败：保留弹窗内的摘要与字段错误，已填写内容不得丢失。
- `409 CONFLICT`：保留当前操作上下文中的可理解提示，通知只能作为补充，不能是唯一反馈。
- `NETWORK_ERROR`、`TIMEOUT`、`INTERNAL_ERROR` 等无法定位字段且不阻断页面理解的失败：使用全局通知。
- 不在请求拦截层对所有非 2xx 自动弹通知：`shared/api/client.ts` 只负责解析并抛出 `ApiError`，是否通知由各页面的失败分流决定，避免与字段错误重复提示。
