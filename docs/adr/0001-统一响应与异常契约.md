# ADR 0001：统一响应、请求标识与异常契约

- 状态：已采纳
- 日期：2026-09-21
- 影响范围：`backend/app/core/`、全部 HTTP 接口、后续前端 API Client（阶段 0 第 5 项）

## 背景

`AGENTS.md` 已规定成功/失败响应的 JSON 形状与错误码语义，但仓库此前没有任何实现。如果由各领域模块自行拼装响应与错误，会出现三种必然的漂移：错误码各自命名、未捕获异常直接暴露堆栈、以及日志无法关联到具体请求。因此需要在第一个业务模块落地前把这个契约固化在 `app/core/`。

本 ADR 记录的是稳定决策；临时任务状态与优先级仍以 GitHub Issues 为准。

## 决策

### 1. 响应包装用显式泛型模型，不用中间件改写响应

路由显式返回 `ApiResponse[T]`，失败响应由异常处理器构造 `ApiErrorResponse`。

被否决的中间件自动包装方案有明确缺陷：它必须区分 JSON、SSE、文件下载与二进制响应，任何遗漏都是静默破坏；且响应体会被两次序列化，OpenAPI 也无法描述真实结构。显式模型的代价是每个路由多写一层 `success(...)`，换来的是类型检查可用、契约可见。

### 2. 错误码是稳定契约，与 HTTP 状态码一一对应

错误码定义在 `app/core/errors.py` 的 `ErrorCode` 中。改名等同于破坏性 API 变更，必须走文档更新流程。

| HTTP | 错误码 | 触发场景 | 抛出方式 |
| --- | --- | --- | --- |
| 400 | `BAD_REQUEST` | 请求语义非法 | `BadRequestError` |
| 401 | `AUTHENTICATION_REQUIRED` | 缺少有效身份 | `AuthenticationRequiredError` |
| 403 | `PERMISSION_DENIED` | 身份有效但无权限 | `PermissionDeniedError` |
| 404 | `RESOURCE_NOT_FOUND` | 领域资源不存在 | `ResourceNotFoundError` |
| 404 | `ROUTE_NOT_FOUND` | 路径未匹配任何路由 | Starlette 路由未命中，由处理器映射 |
| 405 | `METHOD_NOT_ALLOWED` | 方法不支持 | Starlette 路由方法不匹配，由处理器映射 |
| 409 | `CONFLICT` | 与现有状态冲突（重复申请、版本冲突） | `ConflictError` |
| 422 | `VALIDATION_ERROR` | 请求数据校验失败 | FastAPI `RequestValidationError` |
| 429 | `RATE_LIMITED` | 触发限流 | `RateLimitedError` |
| 500 | `INTERNAL_ERROR` | 未捕获异常 | 兜底处理器 |

`RESOURCE_NOT_FOUND` 与 `ROUTE_NOT_FOUND` 都是 404，但前者是业务事实（资源不存在），后者是客户端写错了路径，前端应分别处理。

### 3. 请求标识贯穿日志、响应头与响应体

`request_id` 由 `RequestContextMiddleware` 建立：入站 `X-Request-ID` 通过 `^[A-Za-z0-9._:\-]{1,64}$` 白名单校验后沿用，否则生成 32 位十六进制值。校验是必要的——未校验的入站头会被原样写回响应头并进入日志，构成响应头注入与日志注入。

标识同时写入 ContextVar（供日志读取）与 `scope["state"]`（供外层异常处理器读取）。**两处都要写**：未捕获异常由 Starlette 的 `ServerErrorMiddleware` 处理，它位于本中间件之外，此时 ContextVar 已被重置，只能依赖 `scope` 传递。

所有响应（含 404、422、500）都携带 `X-Request-ID` 响应头与 `meta.request_id`。

### 4. 日志为单行 JSON，访问日志由中间件产出

`JsonLogFormatter` 输出固定字段 `timestamp`、`level`、`logger`、`service`、`request_id`、`message`，调用方通过 `extra=` 追加的字段合并进同一行（如 `event`、`http_status`、`duration_ms`）。

实测中 uvicorn 会给自身 logger 安装 handler 且不向上传播，导致其日志绕过 JSON 格式；同时 uvicorn 的访问日志与本应用日志没有共同标识。因此 `setup_logging` 关闭 `uvicorn.access`，访问日志由中间件统一产出，保证每行都能关联到 `request_id`。

### 5. 配置使用 `JOBARK_` 前缀，`.env` 按进程工作目录解析

仓库根目录的 `.env` 供 `compose.yaml` 使用（`POSTGRES_*`），后端应用的 `.env` 位于 `backend/`。前缀分离避免了把数据库凭据误读成应用配置。所有字段都有默认值，缺少 `.env` 时服务仍可启动。

### 6. 业务路由挂 `/api/v1`，运维接口不带版本

`/health` 保持根路径且不随版本变化，便于探针长期稳定引用；业务领域路由统一挂到 `settings.api_v1_prefix`。挂载点在 `create_app` 内，阶段 1 起各领域模块的 router 在此逐个 include。

### 7. 异常处理只有一处收口

四个处理器覆盖全部失败路径：`AppError`（领域异常）、`RequestValidationError`（校验）、`StarletteHTTPException`（路由级）、`Exception`（兜底 500）。

强制约束：路由与服务层不得出现 `try/except` 兜底、不得吞异常、不得返回裸字符串。响应中的 `message` 与 `details` 永不包含堆栈、连接串、上游原始错误或请求体原文——`RequestValidationError` 处理器会显式丢弃 pydantic 错误里的 `input` 与 `ctx`，它们是用户原文回显的常见来源。

## 后果

**正面**：契约可从 OpenAPI 读到；错误码与状态码一一对应且有测试覆盖；任何响应都能通过 `request_id` 关联到服务端日志；新增模块只需抛异常，不重复实现错误处理。

**代价与约束**：

- 每个路由需要显式 `return success(...)`，不能直接返回业务对象。
- 注册 `Exception` 处理器等价于接管 Starlette 默认的 500 行为；`raise_server_exceptions` 默认为真的测试客户端会重新抛出异常，验证 500 契约时必须显式关闭。
- `uvicorn.access` 被关闭，若以非本项目方式启动服务，需自行保证访问日志仍带请求标识。

## 未覆盖的问题

- 就绪探针（依赖数据库/外部服务可用性）尚未提供，当前 `/health` 只反映进程存活。
- 限流、鉴权与 CORS 尚未接入，相关错误码已预留但无触发路径。
- 分页信息写入 `meta` 的具体结构，待阶段 1 首个列表接口出现时补充。
