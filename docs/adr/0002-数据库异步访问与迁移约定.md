# ADR 0002：数据库采用异步访问范式与迁移约定

- 状态：已采纳
- 日期：2026-09-21
- 影响范围：`backend/app/core/database.py`、`backend/migrations/`、全部领域模块的数据访问代码

## 背景

阶段 0 需要接入 PostgreSQL 16（本地 Compose 容器已验证）、SQLAlchemy 2.x 与 Alembic，并产出可反复执行的迁移。数据访问范式是领域模块的地基，在此确定成本最低。

选型的争议点不是性能——JobArk 是单用户工具，并发极低。真正的动机有两个：一是后续必然接入流式 LLM 调用与 Playwright 浏览器自动化，二者天然异步；二是如果数据库走同步而外部调用走异步，就会出现"同步 IO 阻塞事件循环"或"到处 `asyncio.to_thread`"的混合范式。

一个需要澄清的误解：**异步不改变数据可见性**。两种驱动的 SQL 相同，读到的都是查询时刻数据库已提交的数据；异步只是把等待网络往返的这段时间让给事件循环。异步不等于缓存、不等于延迟、更不等于最终一致。

## 决策

### 1. 数据库 I/O 全异步，纯计算保持同步

- 数据库、LLM、Playwright、外部 HTTP：使用 `async/await`。
- 评分、校验、字段转换等纯 CPU 计算：保持普通 `def`，不加 `async`。给纯函数加 `async` 会在事件循环里同步阻塞，反而更慢且更难测。

### 2. 事务边界显式，且不与外部等待重叠

- 会话依赖 `get_session` **不做隐式提交**。隐式提交会让"忘记提交"和"提交失败"都变得不可见。
- 应用服务的顺序固定为：**取数据 → 结束事务 → 等待外部 → 按需开启新事务写回**。
- 禁止在持有打开事务时 `await` 外部服务。数据库连接是稀缺资源，外部调用可能耗时数十秒（浏览器自动化尤甚），把连接一起拖住会造成连接池耗尽；同时外部调用失败会连带回滚已经完成的数据读取。

### 3. 会话按请求与任务独立创建

每个 HTTP 请求、每个后台任务各自获取会话，不跨请求复用。因此不存在"上一个请求的未提交事务影响本次查询"这类隐蔽问题。

### 4. 模型基类与元数据聚合

- `Base` 定义在 `app/core/database.py`，并携带约束命名约定（`ix_`/`uq_`/`ck_`/`fk_`/`pk_`）。缺少约定时匿名约束由数据库自动命名，降级脚本将无法稳定引用。
- `migrations/env.py` **显式导入**各领域模块的 `models`。自动扫描会漏掉命名不规范的模块，而漏导入的表现是"迁移里悄悄缺少一张表"，属于最危险的静默错误；显式导入漏加时 autogenerate 会直接暴露差异。

### 5. 迁移约定

- `alembic.ini` **不保存连接串**：由 `env.py` 从应用配置（`JOBARK_DATABASE_URL`）读取，避免凭据进入版本库。
- `alembic.ini` **必须保持 ASCII-only**。这不是风格偏好：`configparser` 按*本地编码*读取该文件（中文 Windows 上是 cp936），一个中文字符就会让所有 alembic 命令在动手前抛 `UnicodeDecodeError`。项目约定注释用中文，此处是有记录的唯一例外。Python 3.15 起默认 UTF-8 模式，届时该限制自然消失。
- `prepend_sys_path` 旁必须显式写 `path_separator = os`，否则每条命令都产生 DeprecationWarning（警告即失败的测试会直接变红）。
- 版本号使用可读递增编号（`0001`、`0002`……）而非随机哈希，通过 `alembic revision --rev-id 0002 -m "..."` 指定。
- 首个迁移 `0001_baseline` 为空修订：阶段 0 的验收是"空数据库可重复迁移"，它验证的是迁移链路本身，而不是引入未论证的表结构。

### 6. 迁移的验证方式

迁移必须经真实 PostgreSQL 验证，而不是只断言脚本存在。测试对独立测试库反复执行 upgrade/downgrade：

- 测试库连接串来自环境变量 `JOBARK_TEST_DATABASE_URL`；未设置时跳过数据库测试，使无 PostgreSQL 的环境仍能跑完单元测试。
- 测试库在夹具中自动创建，且**必须与开发库分离**——迁移测试会降到 `base`，连到开发库就是数据清空事故。
- 迁移测试必须是**同步测试**：Alembic 的异步 `env.py` 内部调用 `asyncio.run`，在已运行的事件循环中调用会直接报错。

### 7. 用工具链守住异步正确性

漏写 `await` 不会报错，只会静默不执行——这是异步最大的陷阱，必须由机器而不是评审兜住：

- **Pyright `strict`**（`pythonVersion = "3.14"`，检查 `app`、`tests`、`migrations`）。
- **pytest 警告即失败**（`filterwarnings = ["error", ...]`）。当前唯一豁免是 Starlette 测试客户端内部引用 anyio 弃用别名，属第三方代码，待上游修复后删除。

该护栏已产生实际收益：接入首日即拦下 Alembic 缺失 `path_separator` 的弃用警告，以及 `@asynccontextmanager` 搭配 `AsyncIterator` 返回标注的弃用。

## 后果

**正面**：数据库与外部调用共用一套 `async/await` 范式，不需要在线程池与事件循环之间搬运；事务边界显式且不与外部等待重叠，连接不会被慢外部服务拖死；迁移链路有可重复的自动化证据。

**代价与约束**：

- 所有数据访问代码必须 `await`，纯粹为了"统一"而不加 `async` 的判断标准写在决策 1 中。
- Starlette 把异常处理器第二个参数声明为宽泛的 `Exception`，而分发实际按异常类型匹配，因此 `exception_handlers.py` 中的注册需要一次有注释的 `cast`。
- pydantic-settings 的 `_env_file` 是运行期支持的隐藏参数，未出现在生成的 `__init__` 签名中，测试中需要两处定向豁免。
- 默认 `database_url` 是本地开发占位串（密码与仓库根目录 `.env` 的 `POSTGRES_PASSWORD` 需一致）。未配置时服务仍可启动，但首次查询会以明确的认证失败暴露问题。

## 被否决的方案

- **全同步（Session + psycopg3）**：代码更直观，但后续接异步 LLM 与 Playwright 时要包线程池，范式混杂；本项目的技术栈走向已明确偏异步。
- **应用异步 + 迁移同步（双驱动）**：要维护两套驱动与两个连接串，收益仅是 `env.py` 少十几行。
- **自动扫描 `app.modules.*.models`**：省一行维护，代价是漏建表的静默错误。
- **`testcontainers`**：环境隔离更彻底，但新增依赖且测试机必须常驻 Docker，本地与 CI 启动更慢。
- **不验证迁移**：无法满足"空数据库可重复迁移"的验收。

## 未覆盖的问题

- 就绪探针尚未提供：`/health` 仍只反映进程存活，不校验数据库可用性。
- 连接池参数尚未按真实负载调整（当前仅开启 `pool_pre_ping`）。
- CI 中的 PostgreSQL service 容器属阶段 0 第 6 项。
- 读写分离、缓存层均未引入；若未来引入，必须重新评估"查询即实时"的前提。
