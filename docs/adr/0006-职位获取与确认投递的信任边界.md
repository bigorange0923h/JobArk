# ADR 0006：职位获取与确认投递的信任边界

状态：采纳已确认的产品与信任边界；具体表结构、接口和运行参数为设计建议，实施前按关联 Issue 审核。

## 背景

复制 JD、辅助采集和确认后辅助投递是不同权限和事实来源。内容去重不能充当观察历史；本地材料确认也不能证明平台已接收。延续 ADR 0003、0005 及[分阶段需求](../requirements/job-intake-and-submission.md)。

## 决策

1. 保持个人单用户、领域所有权及现有不可变 JD／正式简历／报告，不引入通用工作流或多租户预留。
2. Job 拥有来源、接受内容、内容版本、获取尝试和公司信息来源；自动化适配器只执行受控平台操作，不能直接修改领域表或 Application 状态。
3. 渠道、获取方式、系统接受时间、平台读取成功时间、内容首次采集时间、平台声明发布时间分别表达。历史未知不从其他时间倒推；同名不自动合并。
4. 采集、模型外发、实际投递分别授权。自动采集不假装用户逐条确认，已有手工内容导入继续核对确认；人工修订与平台候选冲突不得静默覆盖。
5. Application 拥有固定材料清单、逐次发送授权、执行及核实审计。只有可靠回执或明确标注的用户历史陈述，才能经 ApplicationEvent 更新申请投影；执行状态不等于求职状态。
6. 授权绑定实际目标、不可变材料和实际字段／附件字节；任何影响发送内容或目的地的变化使授权失效。外部结果未知禁止盲目重试，取消不能撤销已发生的外部动作。
7. 单个平台分别验证 READ_SEARCH、READ_DETAIL、READ_FORM、SUBMIT、READ_RECEIPT 能力，缺少许可或可靠能力则关闭该能力；复制内容、下载材料、用户自行操作始终是退路。

## 后果与替代

增加少量按阶段交付的领域记录是必要的：快照不能表达相同内容的重复观察和失败；ApplicationEvent 不能单独表达冻结附件与外部结果未知；内存任务不能处理重启后的不确定结果。具体最小表、约束、事务和 API 见[详细设计](../job-intake-and-submission-design.md)。不先创建所有未来表，不以唯一锁声称外部恰好执行一次，不部署通用队列来掩盖平台不支持自动化的问题。
