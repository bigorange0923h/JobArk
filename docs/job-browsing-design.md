# 多渠道职位浏览与匹配设计审查

核对日期：2026-10-05。核对 HEAD：b709491；工作区已有 Profile 与三份文档未提交改动。本次仅增补文档，不把此前设计或已有测试文件当作运行验收。

## 1. 结论与反方检验

可以采用，但需要调整：“最新”改为明确时间维度，“适配”先用可解释摘要。最小方案是在现有 Job 聚合与 Matching 上增加浏览投影，不建立另一套职位或评分系统。需求依据见 [已确认范围](requirements/job-browsing.md)。下文具体字段、接口、默认值和实施步骤均为待确认建议，不能当作已实现或已批准的 schema。

- 最近导入一份两个月前的 JD，会排在新发现记录前，但不是最近发布职位。粘贴旧 HTML 也不能证明刚观察了平台；现有 last_seen_at 实际是系统接受该内容的时间，界面应说明这一局限，不标“平台刚更新”。更精确的内容获取时间可以后另行设计，不默认相信客户端时间。
- A→B→A 复用旧 A，captured_at 不变；按快照时间猜当前内容或观察时间会出错。历史快照是不同内容集合，不是每次观察的完整流水；首版不承诺完整更新事件历史。
- 同公司同标题可能是不同城市、团队、职级；平台 ID 相同也可能重新发布。渠道不是可靠的机会合并键，不引入自动相似度合并。
- 档案增加新事实并不会改写固定简历版本。不能因为最新档案变化就判定基于旧修订的同一正式简历报告失效；应显示其旧资料依据。
- 平台发布时间变化而 JD 内容未变，不使该 JD 的内容匹配自动失效；A 回归且全部匹配输入相同，旧 A 报告可再次适用，但不是新计算。
- 当前引擎只做技能名称字面检索；没有命中可能是简历未引用该事实，也可能是档案没有记录。不能简单把 gaps 数量称为能力差距，命中数量也不应用于适配排序。
- 当前列表逐机会读取当前快照、前端逐机会请求策略预览；分页后应批量查询／投影，不能全量取职位再逐条分析。是否需要更多缓存或游标取决于实际规模，首版不预建队列、评分缓存或采集引擎。

## 3. 列表页面契约（待确认建议）

一行一个 JobOpportunity，未人工关联的跨平台相似职位分别展示。页头说明“已保存职位；刷新只读取系统数据”，匹配上下文始终可见。

| 展示 | 契约 |
| --- | --- |
| 基本信息 | 公司、标题、地点、雇佣类型、机会状态；缺失为未知，机会状态不是平台招聘有效性 |
| 渠道 | 全部来源标签、采用来源标记；展开每个来源的链接和时间，无链接写“无原始链接” |
| 时间 | 主列系统最近观察；次级展示首次发现、采用来源的平台发布时间和当前内容首次采集；有时区说明，平台仅日期不补零点 |
| 当前 JD | 摘录与详情入口、current_posting_id/current_snapshot_id；无当前内容显示不可分析，不以任意历史快照兜底 |
| 策略判定 | 可考虑／待核对／已排除与原因；读取／评估失败独立提示，不冒充可考虑 |
| 匹配摘要 | 四种业务状态、报告时间、目标及版本；最多两条依据／需核对项，查看全部；零条件显示“未识别可分析条件”，不显示适配良好 |

操作：打开详情、打开原始链接（用户主动跳转）、手工录入、平台内容导入、本地刷新、明确点击分析／重分析。浏览不自动计算或外发；打开链接不证明链接仍有效，也不代表后台访问。

筛选建议：公司／标题关键词（不默认全文 JD 搜索）、渠道多选 OR、地点原文关键词、雇佣类型、机会状态、策略判定及策略失败、匹配状态；不同维度 AND。默认全部渠道、ACTIVE、全部策略与全部匹配状态；支持显示归档。渠道筛选只决定机会是否入选，不隐式改变采用来源或匹配 JD；详情可显式选择另一来源。

排序建议：默认最近观察 DESC；另有首次发现、采用来源平台发布时间、机会更新时间，均允许升降序。机会 first_discovered_at=min(所有 posting.first_seen_at)；last_observed_at=max(所有 posting.last_seen_at)，无 posting 为 null。current_source 时间始终来自当前有内容的 posting，可能不同于聚合观察时间。所有排序 null 最后，同值用 opportunity.id DESC 稳定排序。平台时间仅 EXACT／DATE 精度参与排序，DATE 使用已知日期作日级键，注明同日不表示先后；RELATIVE／UNKNOWN／时区不明且无法比较的值排未知组，不用观察时间替代。

分页建议 page/page_size=1/20，可选 20/50/100，上限 100，meta 返回 total/page/page_size；服务端完成筛选、排序后分页，禁止浏览器全量分页。筛选、排序或匹配对象改变回第一页；URL 保存可分享的筛选／对象 ID；详情返回恢复原条件。页码越界给出总数并回最后有效页，零条回第一页。刷新期间写入可能导致跨页重复或遗漏，普通页码不承诺跨请求一致视图；若以后需要稳定信息流再引入游标和读取边界。

状态：初载骨架；初载失败错误＋request_id＋重试，不显示无数据；刷新失败保留旧列表并标“未刷新”；零职位给录入／导入入口，筛选零结果给清除筛选。单项匹配摘要读取失败为“摘要暂不可用”，不能标分析失败；部分来源缺失不阻断整页。快速切换条件只接受最新请求结果。未建档／无修订／未选简历版本显示输入未就绪，不能误称已分析；运行中是附加操作状态，不取代四种结果状态。

## 4. 详情页面契约（待确认建议）

默认“当前保存 JD”区展示机会采用的来源、链接、四类时间、快照 ID 和原文；明确不是平台实时内容。来源切换是本次查看选择，不写 current_snapshot_id，也不更改机会默认来源。展示当前选择与机会默认来源的差别。

历史按来源分组、内容首次采集 DESC、snapshot.id DESC 排序，标记每个页面的当前快照。A→B→A 只有两个内容版本，不能伪造第三次采集；要观察流水须另行设计。点历史后明确“历史 JD”，相关解析／匹配引用该选定快照，返回当前有明确入口。

匹配区默认沿用列表目标；每份报告显示 JD 来源／快照、资料修订、正式简历版本、引擎版本、生成时间、依据／缺口／不确定项。摘要与展开报告使用同一报告 ID。无报告可明确分析，无当前 JD 禁用分析；打开历史报告不替换当前结论。申请记录入口保持实际材料显式选择及既有确认规则，浏览设计不扩大到外部投递。

详情 404 显示不存在与返回入口；版本冲突 409 保留编辑并要求重读，不覆盖；正文／来源读取失败不使用另一来源冒充成功。选择的来源无当前快照时显示无内容，不自动切换到历史版本。

## 5. 字段与 API（待确认建议）

### 时间字段归属

保留 JobPosting.first_seen_at/last_seen_at 与 JobSnapshot.captured_at，不重写历史时间；前两者表示系统正式接受该来源内容的首次／最近时间，预览、取消、重复确认回执、打开详情或单纯刷新不得推进观察时间。历史首次发现不从候选预览倒推。实际平台内容获取时间目前未知。

建议在 JobPosting 增加 publication JSON 值对象，包含 raw_text、precision（EXACT/DATE/RELATIVE/UNKNOWN）、published_at（带时区精确时间）、published_date、timezone、reference_at（解释相对日期的依据）、origin（平台结构字段／页面摘录／人工填写）、source_excerpt、repost_hint（YES/NO/UNKNOWN）。采用 JSON 可避免首版预建发布事件表，但仍需明确 schema、校验和 Alembic 迁移；最终列形式待实施前确认。

- EXACT 有带时区 published_at；DATE 仅日期；RELATIVE 保留“3 天前”原文与可信参考时间，缺少实际内容获取时间时不能以确认时间换算精确发布日期；UNKNOWN 不填合成日期。矛盾／非法值保留待核对原文但不进入精确排序。
- 同 URL/ID 重新发布不创建虚假 JD 内容快照，也不清空 first_seen_at。没有明确平台证据不推断 repost_hint；发布元数据变化经候选预览与确认更新，旧值保留候选确认审计。旧记录缺少日期一律 UNKNOWN，不批量补采或回填观察时间。
- 首版展示当前已确认发布声明，不承诺完整发布事件历史。若需要逐次观察或发布历史，应再设计独立观察记录，不能塞进按内容去重的 JobSnapshot。

### 读取契约

建议扩展 GET /api/v1/jobs 查询参数 q/sources/location/employment_type/status/strategy_state/match_state/sort/direction/page/page_size/match_kind/profile_revision_id/resume_version_id，值与组合非法返回 422，引用不存在 404，无网络平台访问。列表 data 仍为列表，meta 包含分页与 resolved_match_context（固定本次解析出的输入版本），保留统一响应和 request_id。

列表项增加 sources、posting_count、current_source（posting_id/source/canonical_url/publication/first_seen_at/last_seen_at）、current_snapshot_id、current_content_captured_at、first_discovered_at、last_observed_at、strategy_summary、matching_summary；不传完整 JD 或完整报告。latest_snapshot_id/latest_captured_at 先保留兼容别名，标记废弃且写明真实语义；前后端迁移后再删除，不能只改含义。

GET /jobs/{id} 增加 current_posting_id 和语义明确的 current_snapshot，postings 返回 publication；GET /jobs/{id}/snapshots 支持 posting_id 和分页，不破坏归属检查。建议 GET /matches/{id} 定向读取；GET /matches 增加 snapshot/revision/version/kind 筛选与分页。现有 MatchingView 对 listJobs 和历史报告数组的消费须同步兼容分页，不能漏掉旧页面。

matching_summary 包含 state、report_id、attempt_id、analyzed_at、input_refs、engine、stale_reasons、依据／需核对摘要及不确定提示。Job 负责批量浏览组装，Matching 负责报告选择、状态与摘要语义，不把逻辑散落到前端或另建 score 表；筛选状态与返回状态必须基于同一次解析的上下文。读取无需外部确认；分析保持现有本地明确操作，未来 AI 外发单独确认。

### 失败关联缺口

MatchResult 目前仅成功报告，无 status/failure_code；请求失败并不产生可查询历史。建议 Matching 新增轻量 MatchAnalysisAttempt：固定输入／引擎、started_at/completed_at、SUCCEEDED/FAILED、安全 failure_code、request_id、成功 result_id；不保存上游敏感原错，不预建异步任务引擎。非法请求或引用不存在为请求错误，不写虚假分析尝试；有效输入执行失败才记 FAILED。失败持久化须与报告事务分离，否则回滚会丢掉失败记录。字段、不可变终态约束、崩溃中断处理及重试规则须在实施前明确；首版同步执行可将未完成尝试标为结果未知并允许明确重试，不能当失败已证实。

更简单的备选是仅显示本次页面操作失败、不保留持久化尝试；它无法跨刷新可靠展示分析失败，不能满足完整报告状态要求。该取舍需用户确认。

## 6. 报告适用与选择（待确认建议）

默认目标建议为个人资料当前已保存修订，读取时固定 revision_id；没有修订不在 GET 中创建。指定正式简历时使用该版本绑定的 revision_id，不静默换为最新档案；UI 说明“基于修订 N，当前资料为 M”。切换简历版本即换上下文，不自动生成新版简历。

精确适用键为 snapshot_id + revision_id + resume_version_id（PROFILE 为 null）+ match_kind + engine_name/version。fingerprint 复用现有语义，升级解析或规则时引擎版本必须反映变化；不重写旧报告。相同键多报告取 created_at DESC、id DESC。不能仅按机会或最新 report.created_at 取一份报告。

四状态规则：

1. 有同键成功报告：CURRENT，可用于当前输入。若随后同键分析失败，仍展示成功报告并附“最近重试失败”，保留失败时间／编号。
2. 无同键成功且同键最近完成尝试失败：FAILED；可同时提供旧报告入口，不展示其为当前结论。
3. 无同键成功／失败，但有该机会与同目标类型的历史报告：STALE，列 JD、资料、简历或引擎变更原因；旧报告不参与当前适配摘要。
4. 无可关联历史或尝试：NOT_ANALYZED。另一目标类型的报告只作为历史入口，不暗中当成当前结果。

当前输入缺失为 input_not_ready 附加字段；摘要读取失败为接口／局部读取错误，两者不属于 FAILED。运行中保留最后完成状态并禁用重复点击。并发分析时按完成时间及 ID 选择尝试，报告引用本次冻结输入；执行期间资料或 JD 变更时，新报告保存原输入、返回时显示已过时，不追写为新输入。

JD 切到另一 posting，即使正文一样也不同 snapshot_id，首版不跨来源复用结论；发布时间或观察时间变化本身不改变内容匹配键。A 再次成为当前且其余键一致时旧报告 CURRENT，注明历史生成时间。引擎更替导致过时与“输入变化”原因分开显示。

摘要首版可提炼已有字面命中和 UNKNOWN，但不得先承诺已有“简历未表达”证据。后者需 build_report 同时保留档案命中与简历表达检查，输出分开的状态及定位；学历、年限、项目等当前未分析维度明确列为未分析，不从技能推断。未知项不能称已证实不满足，也不按命中比率排序。

## 9. 每日发现与 JD 更新：已确认目标与待确认设计

2026-10-05 用户确认将每日发现新职位与更新已有来源纳入目标，先选一个平台验证后扩展。前文第 1—8 节的浏览首版与当前实现事实仍有效；自动发现不再是未确认的产品目标，但访问与执行方案尚未批准或实现，不因确认目标立即启动采集。

### 最近 JD 的新语义

“最近 JD”表示最近一次成功从平台读取的正文，同时展示 last_platform_success_at、最近扫描结果及当前内容首次采集时间。手工／用户提供内容记录只称“最近保存”，即使其链接属于平台，也不得标成平台扫描成功。失败不推进成功时间、不清空正文、不替换 current_snapshot_id；读取成功但正文未变更新成功观察时间，不新增内容版本。明确平台下架才记录下架证据，403、404、登录页、验证码、网络错误和解析失败不能仅凭状态码推断职位已下架。

现有 last_seen_at 混合了接受手工／导入内容的语义，不能直接改名 last_platform_success_at。建议新增平台成功读取时间与获取方式，历史数据置未知；扫描记录固定本次 source/posting/snapshot 引用，平台读取原文与人工修订需区分。有效平台内容自动保存已确认；自动路径与现有人工导入候选确认路径分别设计，具体冲突规则见第 10 节建议。

### 单平台验证与接入契约（建议）

分开 DISCOVER（按城市、关键词、岗位条件发现来源）与 REFRESH（检查已保存来源）。一个平台允许查询不等于允许读取完整 JD，两项能力分别验收。优先验证官方接口或明确允许的访问方式；不以已登录、浏览器能打开、第三方工具声称可抓取作为稳定访问证明。授权不足的渠道标能力不可用，不承诺接通四站。

适配器输出稳定平台 ID、规范链接、原文、获取时间、日期声明与来源证据；核心 Job 服务负责校验、页面去重、快照复用及事务。每日扫描记录建议包含平台、任务类型、查询条件快照、计划／开始／结束时间、状态、覆盖／未覆盖范围、安全错误和 request_id；每个来源分别记录成功、失败、内容变化与结果引用。单页成功不能把整个平台标扫描成功；分页中断显示部分完成，不把未发现的旧职位当下架。

仅需要一个每日调度入口与平台适配器，暂不引入通用工作流引擎。重叠任务应防重入；每日任务幂等键按平台／任务类型／计划执行日期确定，具体调度时区建议 Asia/Shanghai。受控短暂读取失败可有限重试，验证码／登录失效／禁止访问停止并等待人工。恢复续扫、分页上限和单次预算待确定；避免无限扩展搜索或重试。

匹配自动触发已确认；建议新 JD 或匹配依据变化才生成新报告，同正文同输入复用既有报告，详细规则见第 10 节。新机会元数据保持平台来源声明，不自动填充人工已确认分类；不同平台不自动合并，历史申请材料不变。

### 实施门槛与验收（建议）

先确定一个平台与搜索／更新范围，取得可用且允许的访问方式；验证搜索结果、完整 JD、稳定 ID、发布时间精度与明确下架信号。再以有界样本连续运行，建议观察 7 天并逐次人工对照：遗漏、重复、正文完整度、失效登录、限流及失败恢复；7 天通过只证明样本条件下表现，不宣称长期稳定或全量覆盖。通过后才实施每日调度和扩大范围，失败则记录阻碍并继续支持用户提供内容导入。

最低验收用例：新发现；相同内容；A→B→A；同 ID 重发；局部失败；全部失败；未运行；重复／重叠执行；应用未运行；明确下架与访问失败区分；扫描期间人工修改导致冲突；历史匹配／申请不变。每天执行依赖运行环境：桌面应用关闭或电脑休眠时不能保证按时扫描，必须选择本地常驻、服务器或下次启动补扫，补扫不得伪造过去的成功观察时间。

### 尚需决定

首个平台与允许的访问入口、定时时刻／间隔、策略搜索条件及已有来源更新范围的具体映射、自动匹配对象仍需细化。策略驱动、启动补跑后续定时、自动保存／匹配已确认，见第 10 节；本轮继续仅设计。

## 10. 策略驱动、启动补跑与自动匹配

首个平台已确定为 51job，前文“首个平台待确定”由此更新；平台访问方式尚未验证。

### 已确认决策

用户确认扫描范围由投递策略决定；启动时检查当天是否已跑，没有则后台运行一次，后续定时跑；有效结果保存并自动匹配；区分下架与访问／登录故障。上述决策优先于前文“匹配仅主动操作”和“自动入库待确认”的旧建议。普通浏览 GET／本地刷新仍不启动任务，生命周期调度是独立入口。

### 策略映射（待确认建议）

投递策略是唯一配置入口，不另建一套平行搜索偏好。代码核对：ProfilePreference 有 target_locations、job_types、薪资、remote_preference 和 exclusions，尚无明确目标岗位检索词；ExclusionPolicy 不等于完整平台搜索请求。复用城市及偏好，但岗位检索词、平台地点编码、条件组合与扫描预算需映射或补充明确字段，不从排除公司／行业／JD 关键词反推正向搜索词。缺少必要搜索参数时显示“策略待补全”，禁止无边界全站搜索；不由 AI 猜测目标。

每次运行固定策略版本／查询条件快照；中途策略改变不混入当前批次，下次执行采用新版本。平台不能表达的条件保留为入库后的策略判定，未知分类不能确定排除。更新已有职位范围建议由策略计算并保留明确跟进职位，即使新策略不再命中也提示范围变化，不能静默丢失跟进；该例外待确认。归档／明确下架默认不反复刷新，保留用户重新检查入口。扫描预算限制覆盖范围，不能把截断称完整覆盖。

### 启动与定时（待确认建议）

用户已确认扫描周期为每 1 小时一次。建议服务启动检查完成后建立小时周期：当天未运行则立即后台补跑，并在启动后的每个小时触发后续运行；当天已尝试过则不立即补跑，首次周期在启动后一小时触发。此处“启动后一小时”是建议调度锚点，非已确认具体实现；不默认固定到整点，也不创建 Codex 聊天提醒。重启不重放离线时段，成功观察时间使用实际获取时刻。

一轮超过一小时则跳过重叠触发并记录原因，不堆积无限任务；短暂失败有限重试不能再启动另一完整并发扫描。每小时频率仍受平台授权、接口限额与单轮预算约束，不能解释为可无条件访问平台。平台或任务类型当天部分执行不能把未执行部分标已跑。

“启动”建议指后端服务启动，而不是打开职位页／新浏览器标签，避免多客户端重复运行。按 Asia/Shanghai 日期、平台与任务类型读取持久化任务记录；当天从未开始则后台补跑，当天正在运行则不重复。已开始但失败／中断算“今天尝试过”，不显示“今日成功”；按重试策略或下一定时处理，不在每次刷新／重启无限补跑。跨日启动只补当天，不逐天重放离线期间任务。

后续定时不等于每天只允许一次：幂等键改为平台＋任务类型＋计划时段（含策略版本），同槽重复调度复用执行，后续时段可产生新运行。互斥与带过期／心跳的租约防重入，崩溃后可恢复；当天记录存在不能永久阻止恢复，不能靠进程内布尔变量判断。关机／休眠期间不保证执行，下一启动补当天。周期已确认每小时，具体调度锚点待实施前定稿，本轮不创建实际自动化或常驻服务。

### 自动保存（已确认方向，规则待确认）

成功且领域校验有效的平台内容自动入库，不要求逐条候选确认；人工粘贴导入保留既有确认流程。新机会保存平台声明的公司／标题／地点与来源，不自动设为已核实；稳定平台 ID／URL 去重、事务更新来源当前指向、正文快照复用沿用 Job 服务。重复执行不会重复创建，既有人工元数据不被平台更新覆盖。

原始平台正文必须与人工编辑区分。当前页面手动保存 JD 也会改变 current_snapshot_id，自动刷新可能覆盖人工当前指向；建议只自动推进未发生人工修订的来源，遇到人工修订则保存新平台快照、显示冲突等待选择，同时明确平台最新与采用 JD 各自引用。该保护方案未确认，不能把自动保存理解为自动覆盖人工修改。无完整正文、解析失败、登录页不生成正式 JD；只有摘要可作为独立发现候选，不能送入匹配冒充完整岗位要求。

### 自动匹配（已确认方向，规则待确认）

建议默认用当前已保存 ProfileRevision 为新／变化的当前 JD 自动匹配；指定正式简历版本只在用户配置匹配目标后执行，不猜选简历或对所有版本组合计算。资料修订／目标版本／引擎变更后，对策略范围内来源在下一轮执行重分析；既有有效报告保持可查看。缺档案／修订／完整 JD 标输入未就绪，不能输出虚假报告。

匹配执行固定 snapshot/revision/version/engine；同键有成功报告就复用，正文不变不每天重复分析。键不同才新建报告，失败持久化并有限重试；同键并发任务防重复，主动重分析仍可新建报告。保存成功但匹配失败分别显示，不能撤销真实 JD，也不能把整批称全部成功。当前本地引擎无需外发；以后引入外部模型必须另行确定批量外发同意范围，自动匹配不等于自动同意外发个人资料。
